## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
scripts/check-bundle-size.sh stores baselines keyed by Vite content-hashed filenames (e.g. index-mdfZgkvm.js). Vite regenerates a new hash on every build, so the baseline entries never match: the script prints 'MISSING (not built?)' for the app JS and CSS bundles and still exits 0, reporting '2 passed, 0 failed'. The two files the check exists to guard are the two it skips, so it currently gives false confidence. Baselines should be matched on a hash-independent pattern (e.g. assets/index-*.js) or on total dist size.

## Agent Brief

**Category:** bug
**Summary:** The bundle-size gate skips the two bundles it exists to guard, because baselines are keyed by Vite content hash

**Verification:** Confirmed. The baseline records `assets/index-CFoLN7n8.css` and `assets/index-BLSm3nKc.js`; a current build emits `assets/index-LSfOa7VY.css` and `assets/index-DSmxDgpq.js`. Neither baseline key exists on disk, so the script takes its `MISSING (not built?)` branch and `continue`s without incrementing the failure counter. The "2 passed" it reports are `index.html` and the shared package's `index.js` — the two entries that have stable names and are not what the check is for.

**Current behavior:**
The bundle-size script builds the shared and app packages, then walks a JSON baseline file whose keys are literal output paths. For every key it cannot find on disk it prints a MISSING warning and skips to the next entry without counting a failure. Because Vite regenerates a content hash on every build, the app's JS and CSS entries can never match, so the check exits 0 no matter how much those bundles grow.

**Desired behavior:**
The check resolves hash-bearing bundles by a hash-independent identity, compares their real sizes against the baseline, and fails when growth exceeds the threshold. A baseline entry that genuinely cannot be resolved is an error, not a silently skipped warning — a gate that cannot find what it guards must not report success.

**Key interfaces:**
- The baseline file's shape (currently a map of output path to `{ size, gzip }`). Move the app bundles to a hash-independent key — a glob such as `assets/index-*.js` is the boring option and keeps per-file granularity. If a glob resolves to more than one file, that is an error, not a pick-the-first.
- The script's per-entry resolution step — the only place that needs to learn about patterns. The comparison and threshold logic can stay as-is.
- Whatever regenerates the baseline must write the same key form it reads, or the next build reintroduces the bug.

**Acceptance criteria:**
- [ ] App JS and CSS bundles are matched and compared on a clean build, regardless of their content hash
- [ ] A clean build reports zero MISSING entries
- [ ] An unresolvable baseline entry makes the script exit non-zero instead of skipping
- [ ] Artificially lowering a baseline below the 10% threshold makes the script exit non-zero, and the failure names the offending bundle
- [ ] A glob matching two or more files is reported as an error
- [ ] Regenerating the baseline produces keys the check can read back

**Out of scope:**
- Changing the 10% threshold
- Adding gzip-size enforcement (the baseline records gzip but only raw size is compared today — leave that asymmetry alone)
- Wiring the check into CI or any hook; this ticket only makes it truthful
- Reducing bundle size
