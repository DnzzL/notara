## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
ROOT CAUSE, diagnosed while it blocked a push (not fixed here).

There are three copies of @tiptap/core in node_modules: 2.11.0 twice and 2.27.2 once. TipTap registers commands like toggleHeading by augmenting the ChainedCommands interface with 'declare module "@tiptap/core"'. With several copies resolved, the augmentation lands on one ChainedCommands and the app's editor.chain() is typed by another — so the command exists at runtime and is invisible to the compiler. That is why the editor works and only the type-check complains.

The root package.json overrides pin every @tiptap/* to 2.11.0, which was presumably an earlier attempt at this, but 2.27.2 still slipped in — most likely pulled by @tiptap/suggestion, which is declared as ^3.23.4 in packages/app while everything around it is pinned to 2.11.0. Two copies of suggestion are installed too (3.23.4 and 3.25.0).

So the fix is probably a dependency-resolution one — bring @tiptap/suggestion into the overrides, or move it to a 2.x line — rather than adding the Heading extension. Worth checking whether the neighbouring 'as any' casts (StarterKit at BlockEditor.tsx:100, toggleCode at :505) are workarounds for the same split, in which case they can go with it.

Note this blocks pre-push for everyone, not just for one branch: bun run quickcheck fails on a clean checkout of main, so every push needs --no-verify until it is fixed. That makes it worth more than its Medium priority suggests.

RESOLVED, and my earlier root-cause note was WRONG. Correcting it rather than leaving it.

I claimed the three @tiptap/core copies came from @tiptap/suggestion@3.x pulling core 3.x. Two things were false: suggestion declares core as a PEER dependency, not a dependency, and the divergent copy was 2.27.2 rather than 3.x. Neither is in bun.lock, which resolves @tiptap/core, @tiptap/starter-kit and @tiptap/extension-heading all to 2.11.0.

The actual cause: a stale node_modules. The tree had @tiptap/starter-kit@2.11.0 whose own subtree linked @tiptap/core@2.27.2 and @tiptap/extension-heading@2.27.2 — resolutions predating the overrides block in package.json, never re-resolved. extension-heading@2.27.2 augments ChainedCommands on core@2.27.2, while packages/app is typed against core@2.11.0. Same interface name, two declarations, so toggleHeading existed at runtime and was invisible to the compiler.

Fix: rm -rf node_modules packages/*/node_modules && bun install. One core copy afterwards, and both tsc -p packages/app and bun run quickcheck exit 0.

Corroborating evidence I should have looked at first: CI passed on the PR branch throughout, because CI always installs clean. The failure was only ever local. Checking whether CI agreed with my machine would have found this in one command instead of a dependency-graph investigation.

No dependency change was needed. What ships with this is documentation, so the next person recognises the shape: CONTRIBUTING now says to try a clean install before believing a type error that makes no sense, and explains why two copies of a package whose types augment each other produce exactly this.

**Summary:** Three heading-toggle calls in the block editor's bubble menu fail to type-check, blocking the pre-push gate

**Verification:** Confirmed and reproduced. `bun --bun tsc --noEmit -p packages/app` reports exactly three `TS2339: Property 'toggleHeading' does not exist on type 'ChainedCommands'` errors, all in the bubble menu's H1/H2/H3 buttons. Because the pre-push hook runs the full type-check, pushing to main currently requires `--no-verify`.

**Root cause:** The shared TipTap extension list registers StarterKit through an `as any` cast. That cast erases the module augmentation TipTap uses to teach `ChainedCommands` about the commands its extensions contribute, so the chained command type knows nothing about `toggleHeading`. The neighbouring inline-code button in the same menu already works around this by casting the chain to `any` before calling `toggleCode` — so the codebase has an established convention here, and the three heading buttons simply did not get it.

**Current behavior:**
The heading buttons work correctly at runtime — the commands exist, only their types are missing. But the package does not type-check, so `bun run quickcheck` fails and the pre-push hook rejects every push regardless of what the push contains.

**Desired behavior:**
The app package type-checks clean, the pre-push gate passes on its own, and the heading buttons behave exactly as they do today.

**Key interfaces:**
- The bubble menu's heading buttons, which chain a focus call into a heading toggle with a level argument. Follow the convention the adjacent inline-code button already uses rather than inventing a second workaround.
- The shared extension list's StarterKit registration is the underlying cause. Removing that `as any` would fix the whole family properly, but it is likely to surface further type errors across every command call in the editor. Prefer the local, conventional fix; if you do attempt the root fix, the whole package must type-check clean and no runtime behavior may change.
