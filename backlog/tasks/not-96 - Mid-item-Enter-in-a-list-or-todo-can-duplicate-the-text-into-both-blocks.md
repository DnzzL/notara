## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Splitting a list or todo item mid-text (Enter with the caret inside the text) hands the before/after halves to splitBlock, but does not truncate the current editor's own content. The block's pending debounced save then lands after the split and writes the whole pre-split line back, leaving the text in both blocks. The paragraph/heading/quote branch was fixed under NOT-84 by calling setContent(before, false) before splitBlock; the list and todo branches of the same Enter handler still carry the race (packages/app/src/components/BlockNavigationExtension.ts).
<!-- SECTION:DESCRIPTION:END -->

## Agent Brief

**Category:** bug
**Summary:** The list and todo branches of the Enter handler skip the local truncation that fixes the split/save race, so mid-item Enter leaves the text in both blocks

**Verification:** Confirmed by reading the handler. The paragraph-family branch calls `editor.commands.setContent(splitResult.before, false)` immediately before handing the halves to `splitBlock`, and carries a comment explaining the race — that comment even names this ticket as the remaining gap. The list branch and the todo branch each compute a split result and call `splitBlock` with no equivalent truncation. The mid-text path is the only one affected: the empty-block and cursor-at-end paths in both branches pass `editor.getHTML()` unchanged, which is already correct.

**Current behavior:**
Pressing Enter with the caret inside a bullet, numbered, or todo item computes a before/after pair and creates the new sibling block, but leaves the current editor holding the whole pre-split line. That editor's own debounced save is still in flight; it lands after the split and writes the full line back over the truncated first half. The result is the entire text present in both items.

**Desired behavior:**
Splitting a list or todo item mid-text leaves the head in the original item and the tail in the new one, and stays that way after the debounced save settles. The originating editor is truncated to the head before the split is dispatched, without scheduling a further save of its own — the same shape as the already-fixed paragraph family.

**Key interfaces:**
- The Enter handler's branch dispatch on the block type's split behavior — the `list` and `todo` branches are the two that need the truncation the `split-paragraph` branch already performs.
- The helpers that split a list item and a todo item at the cursor: both already return a before/after pair with inline marks preserved. No change needed there — the head half they return is what the local editor should be set to.
- The content-setting call must suppress the update event, so it does not schedule another debounced save and reopen the race from the other side.

**Acceptance criteria:**
- [ ] Enter mid-text in a bullet list item leaves the head in the first item and the tail in the new one, verified after the debounce window has elapsed
- [ ] Same for a numbered list item
- [ ] Same for a todo item, with the new item's checked state unchecked
- [ ] Inline marks spanning the split point survive on both halves
- [ ] The empty-item and cursor-at-end behaviors are unchanged: an empty item still exits the list to a paragraph, and Enter at the end still creates a new empty item of the same type
- [ ] An e2e spec covers the bullet, numbered, and todo mid-text cases alongside the existing paragraph cases in the Enter spec file, and it fails against the current code

**Out of scope:**
- Reworking the debounced-save mechanism itself, or the block-per-editor architecture (see ADR / the block-per-editor decision — this is a targeted fix inside the existing design)
- The code block branch, which soft-breaks by design
- Shift+Enter behavior in any block type
- Any change that conditionally mounts or unmounts React siblings around the editor component — that pattern crashes remote viewers in live collab
