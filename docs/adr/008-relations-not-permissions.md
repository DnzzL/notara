# ADR-008: Authorization Speaks Relations, Not `domain:action` Permissions

**Status:** Accepted
**Date:** 2026-08-26
**Scope:** The authorization vocabulary. Records why the Policy module has no permission catalogue.

## Context

NOT-104 adopted a composable policy pattern whose reference implementation pairs policies
with a permission vocabulary: a `domain:action` string union (`posts:delete`,
`comments:manage`), generated by a `makePermissions` helper, carried on the principal as a
set, and checked with `permission("posts:delete")`.

Notara took the policies and left the permissions. That is the kind of omission a future
reader — or a future architecture review — will read as an oversight and offer to "fix", so
it is written down here.

The question that decides it: **is there an authorization axis that is not a relation to a
resource?** Counting them:

| Axis | Call sites | A relation covers it? |
| --- | --- | --- |
| Page, block, database, record, field, view access | ~90 | Yes — a relation on the owning page |
| Workspace owner actions (remove member, rotate invite, mail invite) | 3 | Yes — the `owner` role on the workspace |
| Self-scoped operations (my API keys, my workspaces) | 7 | Not authorization at all: the subject *is* the object |
| **Instance admin** (`ADMIN_EMAILS`) | **8** | **No** |

So one axis genuinely falls outside relations. It is a single boolean, driven by an
environment variable rather than stored data.

## Decision

**Express authorization as relations. Do not introduce a permission vocabulary.**

The relation set (`owner` / `editor` / `viewer` on pages, `owner` / `member` on workspaces)
already exists, is stored as tuples, has a declared implication order (ADR-007), and is what
the sharing UI speaks. A `domain:action` union alongside it would be a second language for
the same question, and keeping the two in step would be exactly the duplication the Policy
module exists to remove.

The instance-admin axis is served by one policy, not a framework. Reaching for
`makePermissions` and a generated literal union to express a single boolean is the failure
mode `CLAUDE.md` §5 already names: *if you find yourself reaching for an entitlements
framework for 2 tiers, stop.*

### What this does not decide

Action granularity is a real need and is met elsewhere. Today the mapping from operation to
required relation is implicit at every call site — `checkPagePermission(..., "editor")` for
an update, `"viewer"` for a read — scattered across 68 RPC handlers and 51 REST routes. That
is NOT-122's job: each operation declares `{ resource, requiredRelation }` once. Naming the
action does not require a permission *vocabulary*; it requires an operation table.

## The trigger that would reverse this

**Scoped API keys (NOT-124).** An API key currently authenticates as its owner and carries
every right that user has; `api_keys` has no scope column. For a published REST API shipped
with a CLI, "give my CI a read-only key" is an ordinary request, and relations cannot
express it: a scope is a property of the **credential**, not of the user's relationship to a
resource. That is precisely the shape `domain:action` exists for.

If scoped keys are built, this ADR is superseded in part — not replaced. The policy pattern
absorbs it without restructuring, because permissions in that model live on the principal
and an API key *is* a principal: `CurrentUser` gains a `scopes` field, a `scope(...)` policy
joins the relation policies, and the two compose with `all()`. That is why the door was left
open rather than the framework built speculatively.

Worth deciding before the REST API is advertised. Adding scopes afterwards means either
breaking existing keys or grandfathering them as unscoped forever.

## Consequences

**Positive**
- One vocabulary for authorization, shared by the code, the stored tuples and the sharing UI.
- No catalogue to keep in step with the relations it shadows.
- The single non-relation axis costs one policy instead of a framework.

**Negative**
- Instance admin is expressed as a policy over configuration rather than over data, so it is
  the one decision not visible in the tuple store.
- If scoped keys land, two axes will coexist — relations for resources, scopes for
  credentials — and the composition of the two has to be got right in one place rather than
  per route.
